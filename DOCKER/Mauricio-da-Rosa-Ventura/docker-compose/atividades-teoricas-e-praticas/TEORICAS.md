# Atividades teóricas (seção 10.1 do material de Docker e Docker Compose)

## 1. Diferencie imagem e container usando uma analogia técnica e um exemplo com Node.js

Uma analogia técnica: uma imagem Docker está para um container assim como uma **classe** está para um **objeto** em programação orientada a objetos. A classe (imagem) define, de forma estática, a estrutura e o comportamento — mas não existe "rodando" sozinha; um objeto (container) é uma instância concreta dessa classe, com seu próprio estado em memória, que pode ser criado, usado e destruído, sem alterar a classe original. Da mesma forma, uma imagem Docker (por exemplo, `node:22-alpine`, ou a imagem `hello-multistage` construída na atividade 23 do `step-by-step`) é um pacote somente-leitura com todos os arquivos, dependências e o comando padrão de execução; um container é o processo em execução criado a partir dela, com sua própria camada de escrita, seu próprio filesystem e ciclo de vida — dá para criar vários containers diferentes (`docker run` várias vezes) a partir da mesma imagem, exatamente como dá para instanciar vários objetos da mesma classe, cada um podendo ser modificado independentemente sem afetar os demais nem a "classe" original.

## 2. Explique por que containers não substituem boas práticas de segurança, versionamento e observabilidade

Um container isola **onde** e **como** um processo roda (dependências, filesystem, rede), mas não decide **o que** esse processo faz nem garante, sozinho, que ele foi feito com qualidade. Um Dockerfile que instala uma versão desatualizada e vulnerável de uma biblioteca continua vulnerável dentro do container — o isolamento não corrige a vulnerabilidade, só evita (parcialmente) que ela se espalhe para outros processos da mesma máquina. Da mesma forma, rodar `docker build` sem versionar o Dockerfile e o código-fonte em um sistema de controle de versão (Git) significa que ninguém consegue reproduzir ou auditar exatamente o que gerou aquela imagem; e um container que não expõe logs estruturados nem métricas (observabilidade — Pino/Winston, citados no Módulo 0, seção 14.5) continua uma caixa-preta do ponto de vista operacional, mesmo estando perfeitamente isolado. Em resumo: containers resolvem o problema de "funciona na minha máquina" (ambiente consistente), não o problema de "o código é seguro, versionado e observável" — essas são disciplinas complementares, não substituídas pela containerização.

## 3. Compare volume nomeado e bind mount. Em qual caso cada um é mais adequado?

Um **volume nomeado** (`docker volume create`, ou a sintaxe curta `nome_do_volume:/caminho` em um `docker-compose.yml`, como `mysql_data:/var/lib/mysql` no Cenário 1) é uma área de armazenamento inteiramente gerenciada pelo Docker: o Docker decide onde ela fica fisicamente no host, e ela é portátil entre diferentes ambientes (o mesmo `docker-compose.yml` funciona em qualquer máquina, sem precisar de um caminho absoluto do host). Um **bind mount** (`./backend:/app`, usado nos Cenários 1/2/3 para montar o código-fonte dentro do container) associa um caminho **específico do host** a um caminho dentro do container — o conteúdo é o mesmo arquivo, visto de dois lugares diferentes, e qualquer edição de um lado aparece imediatamente do outro. Volume nomeado é mais adequado para **dados que a aplicação gera e persiste** (o banco de dados, um cache) e que não fazem sentido serem editados manualmente pelo desenvolvedor; bind mount é mais adequado para **código-fonte durante o desenvolvimento**, porque permite editar um arquivo no editor do host e ver o efeito imediatamente dentro do container (hot reload), sem precisar reconstruir a imagem a cada alteração — exatamente o uso dado a eles nos três cenários deste repositório.

## 4. Explique por que `localhost` dentro de um container não representa o host nem outro container

Cada container tem sua própria pilha de rede isolada (namespace de rede, um dos mecanismos do Linux que sustenta o isolamento de containers, citado na resposta da questão teórica 7 do Módulo 0 sobre container x VM). Dentro dessa pilha isolada, `localhost`/`127.0.0.1` sempre aponta para a **própria interface de loopback daquele container**, nunca para a máquina física que o hospeda nem para qualquer outro container rodando ao lado. É por isso que, em `backend/src/index.js` (Cenário 1), a API se conecta ao banco usando `DB_HOST=mysql` (o nome do serviço, resolvido pelo DNS interno do Compose) e não `localhost` — se usasse `localhost`, a API estaria tentando falar com um MySQL rodando dentro do seu **próprio** container, que não existe ali, e a conexão falharia sempre, mesmo com o container `mysql` saudável e rodando ao lado.

## 5. Explique a diferença entre Redis como cache e RabbitMQ como broker de mensagens

Ver a tabela comparativa completa, com exemplo real deste próprio repositório, em [`../cenario-1-vue-node-mysql/ATIVIDADES-PARCIAIS.md`](../cenario-1-vue-node-mysql/ATIVIDADES-PARCIAIS.md#análise--redis-como-cache-x-rabbitmq-como-fila-quando-usar-cada-um). Em resumo: Redis guarda um valor para reaproveitar rapidamente depois (e tudo bem se ele se perder — pode ser recalculado); RabbitMQ garante que uma mensagem publicada será entregue e processada por um consumidor, mesmo que isso demore, porque ela representa um trabalho que precisa necessariamente acontecer.

## 6. Discuta por que o `latest` pode ser perigoso em ambientes profissionais

A tag `latest` não significa "a versão mais recente e estável" — significa apenas "a tag padrão quando nenhuma outra é especificada", e o que ela aponta pode mudar a qualquer momento, sem aviso, cada vez que alguém publica uma nova imagem sem especificar uma tag. Isso cria dois problemas sérios em produção: primeiro, **não-reprodutibilidade** — dois `docker pull minha-imagem:latest` em dias diferentes podem baixar conteúdos completamente diferentes, tornando impossível garantir que o ambiente de homologação é idêntico ao de produção, ou até que um mesmo servidor, reiniciado, suba exatamente o que estava rodando antes; segundo, **rollback impossível de rastrear** — se uma versão nova quebrar algo em produção, não há como saber, só pelo nome `latest`, qual era a versão anterior que funcionava, porque não existe um número ou hash associado a ela. A prática recomendada (usada nos Dockerfiles deste repositório, com `node:22-alpine`, `mysql:8.4`, `postgres:17-alpine` etc.) é sempre fixar uma versão específica, e em produção, idealmente, fixar até o *digest* SHA256 da imagem, não só a tag.

## 7. Explique como Compose melhora o onboarding de novos desenvolvedores

Sem Compose, integrar um novo desenvolvedor a um projeto com múltiplos serviços de apoio (banco, cache, fila) normalmente significa uma lista de instruções manuais — instalar MySQL, instalar Redis, instalar RabbitMQ, configurar cada um, torcer para que a versão instalada localmente seja compatível com a que o resto do time usa — um processo lento e sujeito a divergências ("na minha máquina o Postgres é a versão 14, no seu é a 17"). Com um `docker-compose.yml` versionado no repositório (como os três cenários deste `DOCKER/Mauricio-da-Rosa-Ventura/docker-compose/`), o onboarding se resume a `git clone`, `cp .env.example .env` e `docker compose up -d --build`: a pessoa nova recebe exatamente as mesmas versões de banco, cache e fila que o resto do time usa, sem instalar nada manualmente na própria máquina, e consegue rodar o projeto completo em minutos, no primeiro dia.

## 8. Liste três riscos ao versionar `.env` com credenciais reais

Primeiro, **vazamento público**: se o repositório for público (ou se tornar público por engano, ou for clonado/vazado), qualquer pessoa tem acesso imediato a senhas de banco de dados, chaves de API e tokens — e diferente de uma senha exposta uma única vez, um `.env` commitado fica para sempre no histórico do Git, mesmo que seja removido depois em um commit posterior (é preciso reescrever o histórico inteiro para de fato eliminá-lo). Segundo, **credenciais compartilhadas entre ambientes**: se o mesmo `.env` versionado for usado como base tanto em desenvolvimento quanto em produção, uma pessoa com acesso ao repositório (um estagiário, um colaborador antigo cujo acesso não foi revogado) ganha acesso a produção, mesmo que sua intenção fosse só mexer no código. Terceiro, **dificuldade de rotação de segredos**: quando uma senha precisa ser trocada (por rotina de segurança, ou porque vazou), um `.env` versionado significa que a troca exige um novo commit, revisão e possivelmente um deploy só para atualizar uma senha — em vez de simplesmente atualizar o valor em um gerenciador de segredos externo, sem tocar no código. É exatamente por isso que este repositório versiona apenas `.env.example` (com valores de exemplo, nunca reais) em cada cenário, e cada `.gitignore` deveria (e, na prática de qualquer projeto real, deve) ignorar o arquivo `.env` de verdade.
