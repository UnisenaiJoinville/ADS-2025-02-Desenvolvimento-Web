## 1. Imagem vs. container (analogia + exemplo Node)

**Analogia:** a imagem é a receita de bolo; o container é o bolo assado. A receita é um
arquivo imutável, que pode ser copiada, versionada e usada quantas vezes quiser. Cada
bolo feito a partir dela é uma coisa separada — você pode comer um e o outro continua
inteiro, e nenhum dos dois altera a receita.

Tecnicamente: a **imagem** é um empacotamento imutável, em camadas somente-leitura, com o
sistema de arquivos, as dependências e o comando de inicialização da aplicação. O
**container** é uma instância em execução dessa imagem, com uma camada gravável por cima
e seus próprios namespaces de processo, rede e sistema de arquivos.

**Exemplo Node deste projeto:** o `Dockerfile` da API parte de `node:22-alpine`, copia o
`package.json`, roda `npm install` e copia o código. O `docker build -t cenario1-api .`
produz **uma imagem**. Cada `docker run` a partir dela cria **um container diferente**.
No Passo 3 do roteiro guiado, subi dois containers da mesma imagem em portas diferentes
(3000 e 4000) ao mesmo tempo: dois processos isolados, uma única imagem. Se eu apagar os
containers, a imagem continua no disco; se eu criar um arquivo dentro de um container,
esse arquivo morre com ele e não afeta nem a imagem nem o outro container.

## 2. Por que containers não substituem segurança, versionamento e observabilidade

Container resolve um problema específico: **empacotamento e reprodutibilidade** do
ambiente de execução. Ele garante que a aplicação rode igual em qualquer máquina. Não
resolve mais nada além disso, e tratá-lo como solução geral é um erro comum.

**Segurança:** o isolamento por namespaces é mais fraco que o de uma VM, e todos os
containers compartilham o kernel do host. Uma imagem com biblioteca vulnerável continua
vulnerável dentro do container; um container rodando como root pode ampliar bastante o
estrago de uma falha. Docker não faz varredura de vulnerabilidade, não gerencia segredos
(um `.env` copiado para a imagem fica visível em `docker history`) e não substitui
firewall, autenticação nem princípio de menor privilégio.

**Versionamento:** o Dockerfile versiona o *ambiente*, não o *código*. Sem Git não há
histórico de mudanças, revisão, branch, rollback nem autoria. Pior: `docker build` sobre
código não versionado congela um estado que ninguém sabe reproduzir. Docker e Git são
complementares — o Dockerfile inclusive precisa estar dentro do Git.

**Observabilidade:** `docker logs` mostra o stdout do container e nada mais. Não há
métrica histórica, alerta, rastreamento distribuído nem correlação entre serviços. Com
seis serviços como neste projeto, descobrir *por que* uma requisição ficou lenta exige
métricas e tracing — Prometheus, Grafana, OpenTelemetry. `docker stats` mostra o
instante atual e nada do que aconteceu há dez minutos.

## 3. Volume nomeado vs. bind mount

| | Volume nomeado | Bind mount |
|---|---|---|
| Sintaxe | `mysql_data:/var/lib/mysql` | `./src:/app/src` |
| Onde fica | Área gerenciada pelo Docker | Caminho do host que você escolhe |
| Gerenciado por | Docker (`docker volume ls/rm`) | Você |
| Portabilidade | Igual em Windows, Linux e macOS | Depende do caminho existir |
| Uso típico | Dado que precisa persistir | Código em desenvolvimento (hot reload) |
| Desempenho | Bom em todos os SOs | Ruim no Docker Desktop (Windows/macOS) |

**Volume nomeado** é a escolha para dados que precisam sobreviver ao container: banco,
cache com persistência, uploads. Neste projeto, `mysql_data` e `redis_data` são volumes
nomeados — foi o que fez o registro sobreviver ao `docker compose down`.

**Bind mount** é a escolha para desenvolvimento, quando você quer que a alteração do
arquivo no editor apareça imediatamente dentro do container. No Cenário 1, o frontend usa
`./frontend:/app` justamente por isso. O detalhe importante é o volume anônimo
`frontend_node_modules:/app/node_modules`, que protege o `node_modules` instalado no
build de ser encoberto pela pasta do host — sem ele, o container passa a enxergar o
`node_modules` do Windows, com binários incompatíveis com Linux.

Em produção, bind mount de código é um erro: a imagem deve ser autossuficiente.

## 4. Por que `localhost` dentro do container não é o host

Cada container tem seu próprio **network namespace** — uma pilha de rede independente,
com interfaces e tabela de rotas próprias, incluindo sua própria interface de loopback.
`localhost` (127.0.0.1) sempre significa "esta pilha de rede aqui". Dentro do container
da API, `localhost` é a própria API.

Por isso `mysql://localhost:3306` dentro do container falha com *connection refused*: não
existe MySQL escutando dentro daquele container. O banco está em **outro** namespace, em
outro container.

A comunicação correta usa a rede Docker: `mysql`, `redis` e `rabbitmq` são resolvidos
pelo DNS interno para os IPs dos respectivos containers, como comprovei em aula:

```
$ docker compose exec api sh -c "getent hosts mysql redis rabbitmq"
172.25.0.3    mysql
172.25.0.4    redis
172.25.0.2    rabbitmq
```

Casos correlatos: para o container alcançar um serviço rodando **no host**, usa-se
`host.docker.internal` (Windows/macOS). Para o navegador — que roda no host — alcançar o
container, usa-se `localhost:<porta publicada>`, que só funciona por causa do `ports`.

## 5. Redis vs. RabbitMQ

**Redis** é um banco chave-valor em memória. Leitura não destrutiva: o valor fica lá e
vários clientes leem o mesmo dado. Serve para responder "já calculei isso? me devolve
rápido". Perder o Redis deixa a aplicação lenta, não quebrada — o dado pode ser
recalculado da fonte original.

**RabbitMQ** é um message broker. Leitura destrutiva: a mensagem é entregue a um
consumidor e sai da fila após o `ack`. Serve para responder "faça isso depois, não me
faça esperar". Perder uma mensagem significa perder trabalho que ninguém sabe que
precisava acontecer — por isso fila `durable` e mensagem `persistent`.

**No projeto:** o `GET /agendamentos` usa Redis como cache com TTL de 30s — a primeira
chamada devolveu `"origem":"mysql"` e a segunda `"origem":"redis"`. O
`POST /agendamentos` publica um evento no RabbitMQ, e o container `worker`, separado,
consome e processa (no mundo real, o e-mail de confirmação), sem travar a resposta HTTP.

**Critério:** dado recalculável, para ganhar velocidade → Redis. Trabalho que precisa
acontecer, pode demorar e não pode se perder → RabbitMQ.

## 6. Perigos do `latest`

`latest` não significa "a versão mais recente": é apenas a tag aplicada por convenção ao
último push, e ela **muda de conteúdo com o tempo**. Isso quebra a reprodutibilidade, que
é a razão de existir do Docker.

Os problemas concretos:

- **Build não reprodutível.** `FROM node:latest` hoje traz Node 22; em três meses trará
  Node 24. O mesmo Dockerfile, no mesmo commit, gera imagens diferentes — o "funciona na
  minha máquina" volta, agora dentro do container.
- **Quebra silenciosa e fora de hora.** A atualização acontece quando alguém roda
  `docker compose build --pull`, ou quando o CI faz o pull numa máquina sem cache. O
  build quebra sem que ninguém tenha mudado uma linha de código, e no pior momento.
- **Mudança de major sem aviso.** `mysql:latest` pode pular de 8.4 para 9.x com mudanças
  incompatíveis de autenticação ou formato de dados.
- **Diferença entre máquinas.** Quem tem a imagem em cache roda uma versão; quem clonou
  hoje baixa outra. A equipe deixa de estar no mesmo ambiente.
- **Rollback impossível.** Não dá para voltar para "o `latest` da semana passada".

Por isso todas as imagens deste projeto têm versão fixa: `node:22-alpine`, `mysql:8.4`,
`redis:7.4-alpine`, `rabbitmq:4-management`, `postgres:16-alpine`, `nginx:1.27-alpine`.
Atualizar passa a ser uma decisão deliberada, num commit revisável e reversível.

## 7. Compose e onboarding

Sem Compose, o roteiro de entrada de um desenvolvedor novo é: instalar Node na versão
certa, instalar MySQL, criar o banco e o usuário, instalar Redis, instalar Erlang e
RabbitMQ, habilitar o plugin de management, ajustar portas conflitantes, criar as
variáveis de ambiente e finalmente subir a aplicação. Isso é um dia inteiro no melhor
caso — e cada pessoa termina com um ambiente ligeiramente diferente.

Com Compose, o roteiro inteiro é:

```bash
git clone <repo>
cd projeto
cp .env.example .env
docker compose up -d --build
```

O `docker-compose.yml` é um **contrato técnico versionado**: declara quais serviços
existem, em que versão, como se conectam, o que persiste e quais variáveis são
necessárias. Como está no Git ao lado do código, ele evolui junto — quem adiciona o Redis
adiciona o serviço no mesmo commit, e todo mundo recebe a mudança no próximo `git pull`.

Os ganhos, além da velocidade: o ambiente é **idêntico** para toda a equipe, eliminando a
classe de bug do "na minha máquina funciona"; a documentação de arquitetura para de ficar
desatualizada, porque o arquivo que descreve a pilha é o mesmo que a executa; e o
descarte é limpo — `docker compose down -v` remove tudo, sem deixar serviços órfãos na
máquina, o que torna seguro experimentar.

## 8. Três riscos de versionar o `.env` real

**Risco 1 — Vazamento permanente de credenciais.** O Git guarda histórico: uma senha
commitada continua acessível em commits antigos mesmo depois de removida do arquivo
atual. "Apagar e commitar de novo" não resolve — é preciso reescrever o histórico
(`filter-repo`) e forçar push, quebrando o repositório de todo mundo. Se o repositório for
público, ou virar público um dia, os segredos vazam junto. Existem bots que varrem o
GitHub em tempo real procurando exatamente isso, e credenciais de nuvem expostas assim
são exploradas em minutos. A resposta correta é rotacionar todos os segredos expostos.

**Risco 2 — Um único conjunto de credenciais para todos os ambientes.** O `.env` é o
ponto onde desenvolvimento, homologação e produção deveriam divergir. Versionado, ele
tende a virar o valor de todo mundo — e o caminho natural é acabar com senha de produção
no arquivo que cada desenvolvedor tem na máquina. Isso multiplica a superfície de
exposição por todo notebook da equipe e apaga a fronteira entre "posso quebrar" e "não
posso quebrar".

**Risco 3 — Conflitos constantes e sobrescrita de configuração local.** O `.env` é, por
natureza, local: cada pessoa ajusta portas por causa de conflitos na própria máquina —
como aconteceu neste trabalho, em que 3000 e 8080 estavam ocupadas. Versionado, cada
ajuste vira uma alteração rastreada e um conflito de merge, e um `git pull` pode
sobrescrever a configuração que fazia o ambiente da pessoa funcionar.

**Prática correta:** versionar o **`.env.example`** com todas as chaves e valores fictícios,
e listar `.env` no `.gitignore` — foi o que fiz nos três cenários. Em produção, os valores
vêm de um gerenciador de segredos (Docker Secrets, Vault, AWS Secrets Manager), nunca de
um arquivo em texto puro.
