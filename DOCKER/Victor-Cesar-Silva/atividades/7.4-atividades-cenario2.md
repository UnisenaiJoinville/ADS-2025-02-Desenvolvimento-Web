## Teórica — Diferença entre `ports` e `expose`

`ports` **publica** a porta do container no host: cria uma regra de encaminhamento que
faz o tráfego que chega em uma porta da máquina ser redirecionado para uma porta do
container. É o único jeito de algo de fora da rede Docker — o navegador, o Postman, um
colega na mesma rede — alcançar o serviço.

`expose` **não publica nada**. Ele é apenas documentação: declara quais portas o
container ouve, para quem lê o compose ou o Dockerfile. Containers na mesma rede Docker
conseguem se falar mesmo sem `expose` e sem `ports` — na rede interna, todas as portas
já estão acessíveis entre os serviços.

**Exemplo do proxy neste cenário:**

```yaml
nginx:
  ports:
    - "8082:80"      # publicado: o navegador entra por aqui

app:
  expose:
    - "80"           # só documenta; ninguém de fora alcança o app
```

O navegador acessa `http://localhost:8082`, o Docker encaminha para a porta 80 do
container do Nginx, e o Nginx faz `proxy_pass http://app:80` — uma chamada que acontece
**inteiramente dentro** da rede `web_net`. O container `app` funciona perfeitamente sem
nenhuma porta publicada, porque quem fala com ele é o Nginx, que está na mesma rede.

A regra prática: publique com `ports` **somente** a porta de entrada da aplicação. Todo o
resto conversa por dentro.

## Prática — Subir o cenário 2 e acessar `http://localhost:8080`

```bash
cd cenario2
cp .env.example .env
docker compose up -d --build
curl -o /dev/null -w "HTTP %{http_code}\n" http://localhost:8082
```

**Evidência de acesso:**

```
$ docker compose ps
SERVICE    STATUS                 PORTS
app        Up                     80/tcp
nginx      Up                     0.0.0.0:8082->80/tcp
postgres   Up (healthy)           5432/tcp

$ curl -o /dev/null -w "HTTP %{http_code}" http://localhost:8082
HTTP 200
```

A página React é servida corretamente através do Nginx.

> **Observação:** a porta 8080 do host já estava ocupada por outra aplicação nesta
> máquina, então o Nginx foi publicado em **8082** (`"8082:80"`). Dentro da rede Docker
> nada muda — o Nginx continua ouvindo na porta 80.

Note que o container `app` aparece com `80/tcp` **sem** o prefixo `0.0.0.0:` — isso é
exatamente a diferença visual entre `expose` (só declara) e `ports` (publica no host).

## Prática — `docker compose --profile tools up -d`

```bash
docker compose --profile tools up -d
curl -o /dev/null -w "HTTP %{http_code}\n" http://localhost:5050
```

**Evidência do PgAdmin na porta 5050:**

```
$ docker compose ps
SERVICE    STATUS                 PORTS
app        Up                     80/tcp
nginx      Up                     0.0.0.0:8082->80/tcp
pgadmin    Up                     0.0.0.0:5050->80/tcp
postgres   Up (healthy)           5432/tcp

$ curl -o /dev/null -w "HTTP %{http_code}" http://localhost:5050
HTTP 302        ← redirecionamento do PgAdmin para a tela de login: serviço no ar
```

O serviço `pgadmin` está declarado com `profiles: [tools]`. Isso significa que ele **não
sobe** num `docker compose up -d` comum — só quando o profile é pedido explicitamente. É
o mecanismo certo para ferramentas de apoio: quem só quer rodar a aplicação não carrega
o PgAdmin junto, economizando memória e tempo de boot.

Login configurado pelo `.env`: `PGADMIN_EMAIL` e `PGADMIN_PASSWORD`. Para conectar no
banco dentro do PgAdmin, o host é **`postgres`** (nome do serviço), não `localhost` —
porque o PgAdmin também roda em container.

## Análise — Por que o Postgres não precisa publicar porta no host

O Postgres não publica porta porque **ninguém fora da rede Docker precisa falar com
ele**. Quem consome o banco é a aplicação, que está na mesma rede `web_net` e o alcança
pelo nome `postgres:5432`. O navegador nunca conversa com o banco diretamente — ele fala
com o Nginx, que fala com a aplicação, que fala com o banco. Publicar a porta 5432
não adicionaria nenhuma funcionalidade.

O que ela adicionaria é **superfície de ataque**. Uma porta publicada fica acessível em
todas as interfaces de rede da máquina, não só em `localhost`. Numa máquina de
desenvolvimento em rede compartilhada — o laboratório da faculdade, um café, uma VPN
corporativa — isso significa um banco de dados exposto a qualquer um que consiga alcançar
aquele IP, protegido apenas pela senha do `.env`, que costuma ser fraca em ambiente
local. Bots que varrem faixas de IP em busca de portas 5432 e 3306 abertas são um
problema real e constante.

Há ainda um ganho prático: sem publicar, **não existe conflito de porta**. Se o
desenvolvedor já tiver um Postgres instalado na máquina usando a 5432, ou rodar dois
projetos com Postgres ao mesmo tempo, tudo funciona sem ajuste nenhum. Foi exatamente
esse problema que apareceu neste trabalho com as portas 3000 e 8080 — que estavam
ocupadas e obrigaram a mudar o mapeamento.

Quando é realmente necessário inspecionar o banco, existem dois caminhos melhores do que
publicar a porta permanentemente: entrar no container com
`docker compose exec postgres psql -U app_user -d appdb`, ou subir uma ferramenta de
apoio dentro da própria rede — que é justamente o papel do PgAdmin no profile `tools`.

**Princípio geral:** publique somente a porta de entrada da aplicação. Banco, cache e
broker ficam na rede interna. Em produção essa regra é ainda mais rígida, e o `.env`
local dá lugar a um gerenciador de segredos.
