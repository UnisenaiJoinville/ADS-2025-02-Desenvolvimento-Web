## 1. O que fica exposto e o que fica interno?

**Exposto no host (com `ports`):**

| Serviço | Mapeamento | Por quê |
|---|---|---|
| `frontend` | `8090:80` | é a porta de entrada da aplicação; o navegador roda no host |
| `rabbitmq` | `15673:15672` | apenas o painel de gerenciamento, para demonstração em aula |

**Interno (sem `ports`):** `backend`, `postgres`, `redis`, a porta 5672 do RabbitMQ e o
`worker`.

O critério é: publica-se **apenas o que precisa ser alcançado de fora da rede Docker**.
O navegador é o único cliente externo, e ele fala só com o frontend. O backend é
alcançado pelo Nginx do próprio frontend, via `proxy_pass http://backend:3000` — uma
chamada interna à rede `app_net`. Postgres e Redis são consumidos exclusivamente pelo
backend, e o worker não recebe conexão de ninguém: ele só consome a fila.

Publicar o banco não traria funcionalidade nenhuma e traria dois problemas concretos:
superfície de ataque (uma porta publicada fica visível em todas as interfaces de rede da
máquina, não só em `localhost`, e bots varrem faixas de IP atrás das portas 5432 e 3306)
e conflito de porta com outros projetos — que foi exatamente o que aconteceu neste
trabalho, em que 3000 e 8080 já estavam ocupadas.

Em produção eu fecharia também a 15673: o painel do RabbitMQ ficaria atrás de VPN.

## 2. O que sobrevive ao `down`?

**Sobrevive:** o conteúdo dos volumes nomeados `postgres_data` (dados do banco) e
`redis_data` (dump do Redis), além das imagens construídas.

**Não sobrevive:** os containers, a camada gravável de cada um (qualquer arquivo escrito
fora de um volume), a rede `app_net` e as mensagens que ainda estivessem em memória.

`docker compose down` remove containers e rede, mas **não toca nos volumes nomeados**.
Ao subir de novo, o Docker recria os containers e remonta os mesmos volumes nos mesmos
caminhos — para o Postgres, é como se o processo tivesse sido apenas reiniciado.

Isso foi comprovado na prática no Cenário 1: criei um registro, rodei `docker compose
down`, subi de novo e o registro continuava lá.

```
$ docker volume ls | grep cenario1
local     cenario1_mysql_data
local     cenario1_redis_data

$ curl localhost:3002/agendamentos     # depois do down + up
{"origem":"mysql","dados":[{"id":1,"paciente":"Victor Cesar Silva",...}]}
```

Já `docker compose down -v` apaga os volumes junto, e o banco volta vazio. É a diferença
entre "desligar" e "formatar" — por isso o `-v` merece atenção redobrada e nunca deve ser
o reflexo diante de um erro.

## 3. O que é segredo?

São segredos: `POSTGRES_PASSWORD`, `RABBITMQ_PASSWORD` e, num projeto real, também
`POSTGRES_USER`, `RABBITMQ_USER`, chaves de API, tokens e segredos de assinatura de JWT.

Não são segredos: nomes de serviço, portas, nomes de volume, nome do banco e versões das
imagens — tudo isso está no `docker-compose.yml`, que é versionado.

**Tratamento adotado:** os valores reais ficam no `.env`, que está no `.gitignore` e
**nunca** vai para o Git. O que é versionado é o `.env.example`, com todas as chaves e
valores claramente fictícios (`troque_esta_senha`). Assim o repositório documenta *quais*
variáveis são necessárias sem revelar *quais são os valores*. O `.dockerignore` também
lista `.env`, para que ele não entre na imagem — se entrasse, ficaria visível em
`docker history` para qualquer um que baixasse a imagem.

Versionar o `.env` real seria grave por três motivos: o Git guarda histórico, então uma
senha commitada continua acessível em commits antigos mesmo depois de removida (só
reescrevendo o histórico se resolve); o mesmo arquivo tenderia a valer para todos os
ambientes, colocando credencial de produção no notebook de cada desenvolvedor; e cada
ajuste local de porta viraria conflito de merge.

Em produção, nem o `.env` seria suficiente: qualquer um com acesso ao host lê o arquivo, e
as variáveis aparecem em `docker inspect`. O correto é Docker Secrets, Vault ou AWS
Secrets Manager, com rotação periódica.

## 4. Como provar a comunicação entre os serviços?

Quatro provas independentes, todas executadas neste trabalho:

**a) Resolução de nomes pelo DNS interno** — mostra que o nome do serviço vira IP:

```
$ docker compose exec backend sh -c "getent hosts postgres redis rabbitmq"
172.25.0.3    postgres
172.25.0.4    redis
172.25.0.2    rabbitmq
```

**b) Logs de conexão no boot do backend** — cada dependência confirmada:

```
[postgres] conectado e tabela pronta
[redis] conectado
[rabbitmq] conectado
Backend na porta 3000
```

**c) Endpoint `/health`** — prova viva, checando as três dependências a cada chamada:

```
$ curl http://localhost:8090/api/health
{"status":"ok","postgres":"ok","redis":"ok","rabbitmq":"ok"}
```

Essa chamada prova duas coisas de uma vez: o Nginx do frontend alcançou o backend pela
rede interna, e o backend alcançou os três serviços.

**d) Fluxo ponta a ponta** — a prova mais forte, porque atravessa toda a pilha:

```
$ curl -X POST localhost:8090/api/tarefas -d '{"titulo":"Minha tarefa"}' \
       -H "Content-Type: application/json"
{"id":1,"titulo":"Minha tarefa","evento":"publicado na fila"}

$ curl localhost:8090/api/tarefas     # 1ª vez: cache vazio
{"origem":"postgres","dados":[...]}

$ curl localhost:8090/api/tarefas     # 2ª vez: veio do cache
{"origem":"redis","dados":[...]}

$ docker compose logs worker
worker-1  | [worker] processando tarefa 1: Minha tarefa
```

O campo `origem` alternando entre `postgres` e `redis` prova o cache funcionando; o log
do worker prova que a mensagem saiu do backend, passou pelo RabbitMQ e chegou em **outro
container**. Complementarmente, o painel em `localhost:15673` mostra a fila `tarefas` com
o consumidor conectado.

## 5. Como colegas em 3 sistemas operacionais vão executar?

O mesmo trio de comandos nos três sistemas — é justamente essa a promessa do Docker:

```bash
git clone <repositorio> && cd cenario3
cp .env.example .env          # Copy-Item .env.example .env no PowerShell
docker compose up -d --build
```

O que garante isso é o compose ser um contrato completo: ele declara as imagens com
**versão fixa** (`postgres:16-alpine`, `node:22-alpine`, `rabbitmq:4-management`), a rede,
os volumes e as variáveis. Ninguém instala Node, Postgres, Redis ou RabbitMQ na máquina.

Os cuidados específicos por sistema estão documentados no README:

**Windows 11 sem WSL** — usar o backend Hyper-V (requer Pro/Enterprise; o Home só tem WSL
2), ativando *Hyper-V* e *Plataforma de Máquina Virtual* e desmarcando *Use the WSL 2
based engine* no Docker Desktop. Três armadilhas: caminho do projeto sem espaços nem
acentos; `git config --global core.autocrlf input` antes de clonar, porque arquivos com
CRLF quebram dentro de containers Linux; e a unidade `C:` compartilhada em *Settings →
Resources → File sharing*. Usar PowerShell ou Git Bash, nunca o `cmd`.

**Linux** — o mais direto. Único ponto: adicionar o usuário ao grupo `docker`
(`sudo usermod -aG docker $USER && newgrp docker`) para não precisar de `sudo`, e lembrar
que arquivos criados por volume podem pertencer ao root.

**macOS** — funciona sem ajuste. Em Apple Silicon, todas as imagens escolhidas têm build
`arm64` nativo; se alguma só existisse em `amd64`, bastaria `platform: linux/amd64` no
serviço. Reservar ao menos 4 GB de memória ao Docker Desktop, já que a pilha tem seis
serviços.

E a diferença de porta é resolvida no README: se `8090` estiver ocupada, muda-se apenas o
lado esquerdo do mapeamento (`"8091:80"`) — nada dentro da rede Docker muda.
