## Teórica — Por que a api usa `mysql`, `redis` e `rabbitmq` por nome de serviço e não `localhost`

Dentro de um container, `localhost` aponta para o **próprio container**, não para o host
nem para os outros containers. Cada container tem seu próprio namespace de rede, com sua
própria interface de loopback. Então, se a API tentasse conectar em
`localhost:3306`, ela procuraria um MySQL rodando dentro dela mesma — e não existe
nenhum ali.

O que o Compose faz é criar uma rede bridge própria (`app_net`) e ligar todos os
serviços a ela. Nessa rede existe um servidor DNS interno do Docker que resolve o **nome
do serviço** declarado no compose para o IP atual daquele container. Por isso
`DB_HOST: mysql` funciona: `mysql` é resolvido para o IP do container do banco.

O nome é preferível ao IP porque o IP é atribuído dinamicamente e **muda** a cada
recriação do container. O nome do serviço é estável, faz parte do contrato do
`docker-compose.yml` e continua válido depois de qualquer `down`/`up`.

Prova coletada dentro do container da API:

```
$ docker compose exec api sh -c "getent hosts mysql redis rabbitmq"
172.25.0.3    mysql
172.25.0.4    redis
172.25.0.2    rabbitmq
```

## Prática — `docker compose down` e subir de novo: persistência do MySQL

```bash
curl -X POST http://localhost:3002/agendamentos \
  -H "Content-Type: application/json" \
  -d '{"paciente":"Victor Cesar Silva"}'
# {"id":1,"paciente":"Victor Cesar Silva","evento":"publicado na fila"}

docker compose down          # remove containers e rede — NÃO remove volumes
docker volume ls | grep cenario1
# local   cenario1_mysql_data
# local   cenario1_redis_data

docker compose up -d
curl http://localhost:3002/agendamentos
# {"origem":"mysql","dados":[{"id":1,"paciente":"Victor Cesar Silva", ...}]}
```

**Evidência do volume:** o registro `id 1` continuou existindo depois do `down`. Os
containers foram destruídos e recriados do zero, mas o volume nomeado `cenario1_mysql_data`
permaneceu e foi remontado em `/var/lib/mysql` no novo container.

Se o comando tivesse sido `docker compose down -v`, o volume seria apagado junto e o
banco voltaria vazio — é exatamente essa a diferença entre os dois comandos.

## Análise — Redis vs. RabbitMQ: quando cache, quando fila

| Critério | Redis (cache) | RabbitMQ (fila / broker) |
|---|---|---|
| Propósito | Guardar um valor para ler de novo rápido | Entregar uma mensagem para alguém processar |
| Modelo | Chave → valor, acesso direto | Produtor → fila → consumidor |
| Leitura | Não destrutiva: vários leem o mesmo valor | Destrutiva: a mensagem sai da fila após o `ack` |
| Se ninguém ler | O dado expira pelo TTL, sem problema | A mensagem fica acumulada esperando consumidor |
| Perda do dado | Aceitável — basta recalcular da fonte | Inaceitável — por isso `durable` + `persistent` |
| Pergunta que responde | "Já calculei isso? Me devolve." | "Faça isso depois, não me faça esperar." |

**Exemplo real do projeto — Redis como cache:** o endpoint `GET /agendamentos` consulta
o MySQL e guarda o resultado no Redis com TTL de 30 segundos. Foi possível ver a
diferença na resposta da API, no campo `origem`:

```
1ª chamada: {"origem":"mysql", ...}   ← cache vazio, foi ao banco
2ª chamada: {"origem":"redis", ...}   ← veio do cache, sem tocar no MySQL
```

Se o Redis cair, a aplicação continua funcionando — apenas mais lenta, indo sempre ao
banco. É esse o critério: **cache é otimização, sua perda não quebra a regra de negócio.**

**Exemplo real do projeto — RabbitMQ como fila:** o `POST /agendamentos` grava no banco e
publica um evento na fila `agendamentos`. O container `worker`, separado da API, consome
esse evento e processa (no projeto, loga; no mundo real, enviaria o e-mail de
confirmação). A API responde ao usuário em milissegundos, sem esperar o envio do e-mail.

Aqui a perda **não** é aceitável: se a mensagem sumir, o paciente nunca recebe a
confirmação e não existe forma de recalcular isso a partir de outro lugar. Por isso a
fila é declarada `durable: true`, a mensagem é publicada como `persistent: true` e o
worker só dá `ack` depois de processar.

**Resumo da decisão:** se o dado pode ser recalculado e o objetivo é velocidade → Redis.
Se é um trabalho que precisa acontecer, pode demorar e não pode se perder → RabbitMQ.
