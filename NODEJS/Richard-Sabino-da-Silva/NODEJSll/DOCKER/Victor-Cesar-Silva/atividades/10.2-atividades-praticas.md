vazia, que é justamente a checagem de P2.

## P2 — Rodar `docker compose config` sem erro

```bash
cd cenario1
cp .env.example .env
docker compose config -q
```

**Resultado: saída vazia e código de saída 0 — nenhum erro.**

O `config` faz duas coisas: valida a sintaxe YAML e a estrutura do compose, e faz a
**interpolação das variáveis** do `.env`. É por isso que ele é o teste certo antes do
`up`: se um `${MYSQL_PASSWORD}` não existisse no `.env`, apareceria o aviso de variável
não definida aqui, em um segundo, em vez de virar um erro de autenticação do MySQL três
minutos depois. Sem `-q`, o comando imprime o compose totalmente resolvido, útil para
conferir o que de fato será executado.

## P4 — `exec` dentro da api

```bash
docker compose exec api sh
```

Dentro do container, provando a resolução de nomes pelo DNS interno do Docker:

```
$ docker compose exec api sh -c "getent hosts mysql redis rabbitmq"
172.25.0.3    mysql
172.25.0.4    redis
172.25.0.2    rabbitmq
```

Essa é a prova prática de por que a API usa `DB_HOST: mysql` e não `localhost`: os três
serviços têm IP próprio, em containers separados, e o nome declarado no compose é o que
resolve para esse IP.

Comandos úteis dentro do container: `env` (confere as variáveis que chegaram), `ls /app`
(confere o que o Dockerfile copiou), `hostname` (mostra o ID do container).

## P5 — Perder o container sem perder o volume

```bash
docker compose down                 # remove containers e rede
docker volume ls | grep cenario1
docker compose up -d
curl localhost:3002/agendamentos
```

```
$ docker volume ls | grep cenario1
local     cenario1_mysql_data
local     cenario1_redis_data

$ curl localhost:3002/agendamentos
{"origem":"mysql","dados":[{"id":1,"paciente":"Victor Cesar Silva",...}]}
```

**Evidência:** o container do MySQL foi destruído e recriado do zero, mas o registro
`id 1` continuou lá. O volume nomeado `cenario1_mysql_data` não é removido pelo `down` e
foi remontado em `/var/lib/mysql` no container novo.

Com `docker compose down -v`, o volume seria apagado e o banco voltaria vazio. Essa é a
diferença entre os dois comandos — e a razão de `-v` merecer atenção redobrada.

## P6 — Ativar o profile `tools`

No Cenário 2, o PgAdmin está declarado com `profiles: [tools]`:

```bash
docker compose up -d                    # pgadmin NÃO sobe
docker compose --profile tools up -d    # agora sim
```

```
SERVICE    STATUS                 PORTS
```

Serviços com `profiles` ficam fora do `up` padrão. É o mecanismo correto para ferramentas
de apoio: quem só quer rodar a aplicação não carrega o PgAdmin, economizando memória e
tempo de boot.

## P7 — Adicionar healthcheck até aparecer `healthy`

```yaml
mysql:
  healthcheck:
    test: ["CMD", "mysqladmin", "ping", "-h", "localhost"]
    interval: 10s
    timeout: 5s
    retries: 10
```

```
$ docker compose ps
cenario1-mysql-1  ...  Up 10 seconds (health: starting)
$ docker compose ps
cenario1-mysql-1  ...  Up 7 minutes (healthy)      ← healthy
```

O `depends_on` com `condition: service_healthy` só libera a API depois que esse
healthcheck passa — e não apenas quando o container existe.

**Problema real encontrado e corrigido nesta atividade.** O healthcheck original do
RabbitMQ era `rabbitmq-diagnostics ping`, e a API morria no boot:

```
api-1  | [redis] conectado
api-1  | Falha ao iniciar: connect ECONNREFUSED 172.25.0.2:5672
api: Exited (1)
```

Diagnóstico: `ping` verifica apenas que o processo Erlang responde — ele fica `healthy`
**antes** de a porta 5672 aceitar conexões. O `depends_on` liberava a API cedo demais.

Correção aplicada:

```yaml
rabbitmq:
  healthcheck:
    # check_port_connectivity só passa quando a porta 5672 aceita conexão de fato
    test: ["CMD", "rabbitmq-diagnostics", "check_port_connectivity"]
    interval: 10s
    timeout: 10s
    retries: 15
```

Somada a `restart: on-failure` na api e no worker, a pilha passou a subir de forma
confiável. Lição: o healthcheck precisa testar **o que o dependente realmente usa** — a
porta —, não só se o processo está vivo.

## P8 — Documentar ≥3 erros comuns no README

Documentados na seção *Troubleshooting* do `README.md` de cada cenário. Os cinco erros
abaixo aconteceram de fato durante este trabalho:

**1. `Bind for 0.0.0.0:3000 failed: port is already allocated`**
Outra aplicação já usa a porta no host. Descobrir com `netstat -ano | findstr :3000` e
mudar o lado esquerdo do mapeamento (`"3002:3000"`). O lado direito é a porta dentro do
container e não deve mudar.

**2. `connect ECONNREFUSED <ip>:5672` — a api sobe e morre**
O healthcheck do RabbitMQ passou antes de a porta aceitar conexões. Corrigido trocando
`ping` por `check_port_connectivity` e adicionando `restart: on-failure`. Diagnóstico com
`docker compose logs api` e `docker compose ps -a` (o `-a` é essencial: containers que
morreram somem do `ps` normal).

**3. `getaddrinfo ENOTFOUND mysql` ou conexão recusada em `localhost`**
Uso de `localhost` no lugar do nome do serviço. Dentro do container, `localhost` é o
próprio container. Conferir com `docker compose exec api sh -c "getent hosts mysql"`.

**4. `Access denied for user` no MySQL depois de trocar a senha no `.env`**
A senha só é aplicada na **primeira** inicialização do volume; depois disso o dado
persistido manda. Como é ambiente local: `docker compose down -v` e subir de novo.

**5. Alteração no código não aparece**
A imagem foi construída com o código antigo. Rodar `docker compose up -d --build`. Se
persistir, `docker compose build --no-cache <serviço>`.
